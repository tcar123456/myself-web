## 一句話定位（Hero 區）

> 我自己在做遊戲幣的買賣，這套系統每 5 秒替我看一次價格，便宜的貨一出現就通知我，並且直接算出這一單到底賺不賺。再用累積的實際紀錄回頭比對，找出真正該進貨的時段。

## 適合誰看

- **潛在客戶**：想看「能不能幫我自動盯著外面的價格 / 把散落的數字算成能決策的結論」的老闆
- **技術審視者**：想看資料抓取、時間序列統計、失敗偵測、對帳系統設計的同行
- 想看「用累積的資料回頭推翻自己直覺」這件事怎麼落地的人

## 定位（誠實版）

這是**自有事業的營運工具**，不是接案、不是 SaaS。使用者本人就是幣商，系統天天在跑、每一筆判斷都對應真金白銀。

它跟站上其他案例的**互補之處**：

- 美甲預約系統展示的是：LINE 生態系整合、對外服務流程
- 社區收費系統展示的是：對帳、單據、資料不能出錯
- **這案展示的是**：自動抓外部平台資料、時間序列統計分析、以及「錯了會賠錢」等級的可靠度設計

## 動機與情境

進貨那一端全是難處：

1. 對方平台的價格一直在動，越便宜的貨消失得越快，常常一兩分鐘就被別人買走——人不可能二十四小時盯著
2. 賺不賺錢不是看價差，中間有一層 5% 的遊戲官方手續費，算錯方向整單就反過來
3. 「什麼時候進貨最便宜」全靠同行的口耳相傳，沒有人拿資料驗證過
4. 平台上有假便宜：掛離譜低價騙點擊、或價格低但起售量大到根本吃不下

## 解決方案

**案例頁的四個功能（順序＝四張截圖的順序，一個技術名詞都不能有）**：

| # | 標題 | 對應截圖 |
|---|---|---|
| 1 | 一整天的行情，攤開在同一頁 | `price-trend.png`（走勢報表） |
| 2 | 幾點進貨划算，直接排成一張表 | `hourly-ranking.png`（時段榜單） |
| 3 | 哪一天、幾點鐘，圖上直接分得出來 | `weekday-pattern.png`（星期 / 平日週末） |
| 4 | 便宜的貨一出現，手機就響 | `alerts.jpg`（Telegram 告警） |

**截圖上看得到的實際數字**（2026-09-04 當下的滾動視窗）：

- 同一天之內的價差 **7.7%**，期間趨勢 **+0.3%／天** → 當天買、當天報，不壓庫存
- 涵蓋 **8 天**（123 格來自掛單事件、46 格是快照近似）
- 排除疑似假單 **20 筆**／1,292 筆掛單中
- 平日 vs 週末的 24 小時曲線：清晨六點前後最貴、上午十點附近最便宜，週末起伏比平日大

> ⚠️ **不要把時段榜單的第一名當成定論。** 目前只有 8 天樣本，系統原本會在樣本不足時自己標警告。
> 文案寫的是「系統做了什麼」＋「目前累積 8 天，天數還在往上疊」，**沒有斷言「週四早上最便宜」**。
> 樣本累積到六週以上再談「哪一天」。

## 技術棧

| 層 | 技術 |
|---|---|
| 語言 | Python 3，**零第三方依賴**（只用標準庫） |
| 資料抓取 | urllib + 平台官方 JSON API，每 5 秒一輪、上限併發 4 |
| 儲存 | SQLite（WAL）on volume：取樣 / 掛單 / 掛單事件流 / 盤面快照 / 告警 |
| 統計分析 | 手寫 `statistics` + `math`：去趨勢殘差、滾動中位、掛單存活分析。無 pandas / numpy |
| 圖表 | 自製內嵌 SVG：折線 / 長條 / 星期×時段熱力圖。無 matplotlib |
| 報表匯出 | 自製 .xlsx 產生器（`zipfile` + 手寫 XML），無 openpyxl |
| 推播 | Telegram Bot API，背景佇列 + 專屬執行緒，訊號分級靜音。**盤面告警與訂單通知是兩隻 bot** |
| 圖片辨識 | Gemini 2.5 Flash 讀進貨回報表 + 四重驗算，永遠不直接入帳 |
| 對外前台 | LINE Messaging API + LIFF（金額即時試算） |
| 部署 | Zeabur，GitHub push 自動上線，SQLite 掛 volume |
| 測試 | 標準庫 `unittest`，18 支測試檔、914 個測項 |

規模：**11,151 行程式 + 10,435 行測試**，18 天 58 commits。

## 關鍵亮點

### 1. 本來在寫爬蟲，寫到一半發現平台有官方 API

最初真的在解析網頁。寫到一半才發現平台自己有免授權的 JSON 介面，防爬頁上還寫著「若您有高频次访问请求，请使用接口访问」——高頻是官方鼓勵的。實測對比之下沒有懸念：

| | 官方 API | 網頁解析 |
|---|---|---|
| 壓力測試 | 214 次/分鐘零失敗 | 48 次/分鐘就被擋 |
| 回應大小 | 約 1 KB | 約 137 KB（差 135 倍） |
| 官方立場 | 明確鼓勵高頻 | robots.txt `Disallow: /` |

爬蟲那半套直接丟掉。雲端連續跑 16 小時、6,604 次取樣，失敗率 0.0%。

### 2. 對方被擋時回的是 HTTP 200，不是錯誤碼

全系統最關鍵的一段。防護頁回 200 帶假頁面，不主動檢查就會被讀成「盤面一筆掛單都沒有」→ 加權均價變 0 → 推播一批不存在的超便宜貨。所以每次取樣要過五道判定，任一不過整批丟棄——不寫快照、不更新時間、**絕不標記掛單消失**。

> 這個系統的失效模式是「安靜地算錯」而不是崩潰。

### 3. 「這一小時多少錢」不能用五分鐘一張的快照算

實測 2,004 筆告警掛單：便宜的那批有 **52~61% 活不到一個快照間隔**，比行情便宜 10~15% 的更是 **82%** 撐不過去——快照結構上就看不到要買的那批單。於是另建只增不改的掛單事件流，價格重新定義成「那一小時盤面上最便宜的 10 筆平均」。

### 4. 比時段要先把趨勢扣掉

舊算法「除以當天中位數」拿不掉一天之內的斜率。2026 年八月下旬那段行情每天跌 4.8%，23:00 算出來 −0.2%、跨過午夜的 00:00 跳到 +5.7%——那是換日不是漲價。改成去趨勢殘差後，「最貴時段」從 00:00 移到 05:00、日內價差從 8.8% 縮到 6.5%。**舊算法會叫人在錯的時間賣。**（那是當時那段行情的數字，報表上的日內價差與期間趨勢會隨行情自己重算。）

### 5. 一個欄位的誤解讓系統錯了 17 天

平台回傳的「數量」是單件數量、不是庫存，庫存要再乘發佈件數。深度低估 2.6~14.8%，告警印的數量其實是起售量——一筆實際有 4,900 萬的貨被印成 100 萬，看起來只有一點點就被跳過。更正時**刻意保留舊欄位不動**、新增一組正確口徑並存，因為就地改掉會讓走勢圖在部署當天無聲跳升 12%。

### 6. 盤面告警與訂單通知走兩隻不同的 bot

一開始共用一隻。低價告警一天上百則，客人送出的訂單訊息夾在中間根本看不到——而訂單是會跑掉的，告警漏一則只是少賺一單。拆成兩隻 bot、兩個對話之後，告警照樣洗版，訂單那邊一天只有幾則、一響就知道是生意上門。

### 7. 測試對準「錯了會賠錢」的行為

10,435 行測試守的是不變式，不是覆蓋率：取樣失敗絕不標記掛單消失、掛單編號當北京時間解析（錯了全部時間差 8 小時）、單位不符必須判定失敗。**任何程式碼的新增或修改都必須附測試，沒有例外。**

## 成果

- 上線狀態：**已上線運作中**（2026-08 起，持續維護）
- 取樣可靠度：部署驗證 16 小時 6,604 次取樣，失敗率 0.0%
- 告警速度：從對方掛出來到手機收到通知，通常不用十秒
- 決策依據：把「什麼時候進貨便宜」從口耳相傳變成可以逐週累積、逐週修正的表
- 🟡 待補：實際省下的時間 / 因為告警多吃到的單數 / 營收影響（**使用者自行填，不要推估**）

## 揭露界線（硬規則）

作品集是公開可訪問的，這個案例的資料是真金白銀的營運資訊。

**可以寫**：5 秒一次的節奏、涵蓋天數與掛單筆數、取樣失敗率、日內價差與期間趨勢百分比、平日／週末的時段曲線、5% 遊戲官方手續費、程式與測試行數、API vs 網頁的壓測對比。

**絕對不可以寫**（連在草稿裡都不要留實際數值）：

- 保本比值、賺 10/15/20% 的報價階梯、實際成交均價、使用的匯率
- 任何實際金額（進貨額、收益、淨利）、分潤比例
- LINE 官方帳號 ID 與暱稱、LIFF ID
- 線上服務網址、GitHub repo 網址（私有）
- 對岸代收合作夥伴的代稱 → 一律寫「對岸的代收合作夥伴」
- 平台的內部識別碼
- **遊戲全名 → 一律寫「XX谷」**
- **具體伺服器名稱與 API 用的伺服器 key → 一律寫「四個伺服器」**
- 平台名稱 → 寫「對岸的遊戲幣交易平台」（既然遊戲名要遮，點名平台等於還是查得到）

**截圖已處理的部分**：`alerts.jpg` 已塗掉報價階梯的 12 個比值與 3 處匯率值（保留「保本 比值」「賺 10% 比值」「匯率」「遊戲手續費 5%」這些標籤）；`price-trend.png` 已塗掉圖上未遮到的伺服器 key。**日後換新截圖必須重做這兩件事。**
